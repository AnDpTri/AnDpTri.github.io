Vietnamese Address Normalization to the New Administrative Units after the 2025 Merger

An offline, CPU-only system (no LLM, no external API) that turns free-form Vietnamese addresses into structured addresses under the administrative units in effect since 1 July 2025: 34 provinces, no district level.

Natural Language Processing course project · Python · PyTorch · LightGBM · python-crfsuite

86.8%full-address accuracy (6 fields) on a 400-address real OSM development set
69.8%on a separate test set whose labels are not yet hand-verified
~75 msper address, one thread of a laptop CPU
34provinces, no district level

The problem

People type addresses without diacritics, with abbreviations (HN, TP.HCM, ng., kp), typos, shuffled order, missing commas, or in the old administrative boundaries. The system returns the house number, alley, hamlet, street, commune or ward and province in official form, plus a full normalized string and a list of warning flags.

Rules the system follows

  • Missing information stays empty; the system does not guess.
  • If something is present but ambiguous (for example a name repeated in several places) it returns the best answer and adds a warning flag.
  • The district is used only to identify the right commune and province; it is not in the output.
  • A commune that was split into several new ones is resolved by street name when the lookup table has evidence; otherwise the field is left empty with a flag and the candidate list.

How it works

  • Part 1, preprocessing: a Char-CNN + CRF tags each character with one of seven roles; a trie proposes administrative candidates (exact, unaccented, initials, misspelled); a beam search assembles valid paths on the old and new administrative trees; a LightGBM ranker (LambdaRank) chooses between hypotheses; old district and commune names and a street dictionary are looked up.
  • Part 2, conversion: a clean old address is converted to the new units by a lookup table only; split communes follow the rule above.
  • The deployed model is small (a 1.4 MB CNN plus the ranker) and runs offline. A small web demo wraps the same configuration used for measurement.

Results

Speed was measured on one thread of a laptop CPU over 300 development sentences with the model already loaded: 74.9 ms on average, 72.8 ms median, 138.9 ms at the 95th percentile.

How to read the numbers

  • 86.8% is a development-set number. The development set was used to choose the configuration, so it is not an independent measurement.
  • The generated and hard sets were written by the same AI helper as the training data (different seeds and street names), so gains on them can be inflated.
  • test400 has AI-assigned labels that nobody has checked and it was opened many times, so it is no longer a held-out set. A hand-verified held-out set is the next step.

What I tried and dropped

  • ViDeBERTa-xsmall: 1–2 points worse than the CNN on every measure and about twice as slow on CPU (117 ms vs 54 ms per sentence), so it was dropped. PhoBERT stopped at the preparation stage.
  • Training on 15,000 extra OSM addresses labelled from tags made the test result worse (248 to 227 correct), because OSM merges house numbers into street names.
  • Adding 10,000 synthetic noisy addresses lifted the hard set from 57.2% to 82.7% while the dev set stayed the same; this one was kept.
  • A lookup that resolves split communes by street name (197 rows, 66 communes) kept all 280 held points correct.

Known issues

  • Hamlet boundaries when there is no comma (“xóm 5 xã mỹ hưng huyện…”); a fix is in progress on a separate branch.
  • Abbreviations that drop vowels (“hnoi”) cannot be looked up and are left empty.
  • Weak spots on the wide-coverage set: newly formed communes (about 86% correct), old names, and addresses with only a commune name.
